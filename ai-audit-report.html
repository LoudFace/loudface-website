The one-paragraph answer

You're right that it's not working — and it's more fundamental than "doesn't look good."

The audit runs on a Redis database that has been deleted or expired (redis-10243…cloud.redislabs.com no longer resolves at all). So the very first thing every submission does — write a record — hangs, the function eventually times out, and the visitor gets a red "Network error." I reproduced this three separate ways. That alone means it currently converts zero visitors, by mechanism, not by chance.

But fixing Redis only gets you back to a lead magnet that was already leaking: it asks for 5 fields and throws away 3 of them, makes the visitor stare at a progress bar for 3–5 minutes, then shows a report at a URL it never emails them — while the page's own FAQ promises "we send you the report" and the hero promises "a personal Loom from Arnel." Neither is wired to anything. And when the lead reaches the end and clicks the one call-to-action — "Book a Free Strategy Call" — nothing happens: that button's booking handler isn't loaded on the results page. When a lead does complete, nobody at LoudFace is notified, and the record self-deletes after 30 days. On top of that, Google sends it 0 clicks and it's linked from almost nowhere on the site. The engine that produces the report (the 15-slide deck) is actually the best part — clean and honest. The problem is everything around it.

1 · Why it's not working — the production outage

This is the headline. One dead dependency takes the whole tool down.

P0The Redis instance backing the audit no longer exists✓ reproduced 3×

The audit stores every record, its progress, and its rate-limit counters in a single Redis Cloud instance. That host — redis-10243.crce219.us-east-1-4.ec2.cloud.redislabs.com — now fails DNS resolution entirely (getaddrinfo ENOTFOUND). The free/trial database was deleted or expired. Because getRedis() is the first call in the submit path, and Redis is also read on the results page, nothing in the flow can complete.

Reproduced: (1) live POST /api/audit hangs >120s then the connection is dropped; (2) GET /api/audit/<id>/status hangs >30s; (3) the browser end-to-end test submitted a real audit and got net::ERR_CONNECTION_CLOSED → the on-screen "Network error — please try again" (see appendix). A direct connection attempt to the host from this machine returns ENOTFOUND in 178ms.

Fix: provision a new Redis (Vercel Marketplace Upstash/Redis, per the project's own Vercel guidance), set REDIS_URL, redeploy. Then add a health check so a dead datastore pages you instead of silently 500-ing every lead. This is a ~30-minute unblock, and until it's done nothing else here matters.
P1When the backend dies mid-run, the audit is stuck "processing" forever and the visitor watches a frozen bar with no end✓ confirmed in code

The results page polls /status every 3 seconds with no attempt limit and no elapsed-time ceiling (AuditProgress.tsx). If the background job is killed (Redis blip, function timeout), the record never flips to failed, so the client polls indefinitely, showing a rotating "still working…" tagline and a stuck percentage. The reassurance copy even says "bookmark this page and come back" — to a page that will never resolve.

Fix: add an elapsed-time cutoff (~8 min) that swaps to a "taking longer than expected — we'll email you / try again" state, and a staleness check so processing records older than N minutes read as failed.

2 · The lead engine is broken by design

This is the part that answers "it's not doing its job." Even with Redis alive, the lead lifecycle leaks at every stage.

P1The one "Book a call" button in the whole tool does nothing when clicked✓ verified

The final slide's "Book a Free Strategy Call" button (CTASlide.tsx:26) is a bare data-cal-trigger button — no link, no handler of its own. It relies entirely on the site's Cal.com click-handler to open the booking modal. But the audit route runs on its own stripped layout whose comment says it outright: "site chrome is not inherited — no Header/Footer/Webflow-badge/Cal/Leadsy." So the Cal handler is never loaded on the results page. A lead reads the whole report, reaches the one call-to-action, clicks it — and nothing happens. After the dead Redis, this is the most important finding: even a fully working audit cannot convert, because its single conversion action is inert.

Fix: mount the Cal handler/embed in the (audit) layout, or make the button a real link to the booking URL. Then click-test it end-to-end.
P1The report is never emailed — yet the page promises it is✓ verified

There is no email delivery anywhere in the audit (the email module email.ts was built then deleted in commit afaf9e9; no resend/sendgrid/nodemailer exists). The visitor only gets a URL. But the page's FAQ says verbatim: "We run your audit and send you the report. That's it." That's a claim the product cannot keep — a claims-integrity problem on a page whose whole pitch is trustworthy data.

Fix: either wire real email delivery of the report link on completion (re-add Resend), or rewrite the FAQ + reassurance copy to describe what actually happens ("your report opens in the browser — bookmark it"). Don't ship a promise with no mechanism.
P1"A personal Loom from Arnel" is promised 5 times and delivered 0 times✓ verified

The phrase appears in the meta description, OG tags, Twitter card, and twice in the on-page "What you get" list. A search of the entire results flow — all 15 slides, both progress screens, the CTA — for "loom" returns zero matches. Nothing captures that a Loom is owed, notifies Arnel to record one, or tells the visitor when it's coming. It's a manual founder promise with no operational hook, made worse by the fact the audit doesn't email anyone — so Arnel doesn't even know an audit ran.

Fix: if the Loom is the real differentiator, make it a tracked deliverable — completion fires a notification to Arnel with the audit link + lead details, and the UI tells the lead "Arnel will send your Loom to {email} within 1 business day." Otherwise cut the claim.
P1A completed lead notifies nobody and evaporates in 30 days✓ verified

A submitted lead (email, url, name, competitors, persona) is written only into the Redis record with a 30-day TTL, plus a single PostHog event (audit_form_submitted). There's no CRM sync, no Slack/email alert, no admin list, no export. So: no one is told a lead arrived, and the only durable record is a PostHog event — the one system that's just an analytics ping, not a lead workflow. The Redis lead literally deletes itself after a month.

Fix: on submit, fire a notification (Slack/email to Arnel) and push the lead to your CRM/HubSpot. Persist leads outside the 30-day audit TTL. A lead magnet that doesn't route leads to a human isn't a lead magnet.
P25 required fields, 3 of them thrown away server-side✓ verified

The form requires website, name, email, top-3 competitors, and buyer persona. The API reads only two: const { url, email } = body; (route.ts:56). contactName, competitors, and buyerPersona are received and silently dropped. The competitors field is the cruelest — you make the user list 3 competitors, then the pipeline auto-detects competitors via DataForSEO and ignores what they typed. That's pure friction: three extra required fields, on a form that already asks for a work email, feeding nothing.

Fix: pick one — either use these fields (seed the competitor set from the user's input; tailor the category prompts to the stated persona), or cut them to just URL + email like the legacy form. Every required field on a lead form must earn its conversion cost.
P2"Try Again" dumps the user on a different, inferior form and loses everything they typed

On failure, the retry button routes to /audit — the bare 2-field legacy form — not back to /ai-audit where they came from, and with no prefill. Even the URL and email the backend actually uses are gone. After a 3–5 minute wait that failed, the user re-enters everything into a worse form.

Fix: resubmit the stored record, or return to /ai-audit with url/email prefilled.
P2There's a polished sample report — and it's linked nowhere

A realistic, fully-built demo deck lives at /audit/demo and is referenced from no page on the site. Prospects are asked to hand over a work email + 5 fields with zero preview of what they get. A "see a sample report" link is the single cheapest conversion lift available here.

Fix: link /audit/demo from the hero form and the FAQ ("See a sample report →").

3 · Security & cost exposure

The tool fetches attacker-supplied URLs server-side and bills real money per run. Both guardrails are bypassable.

P1Server-Side Request Forgery — the URL filter is bypassable with a wildcard-DNS trick✓ I verified the bypass

The audit fetches the visitor's URL server-side (to read the brand name) with redirect: 'follow' and no check on where it resolves. The "looks like a domain" regex rejects raw IPs and localhost — but I confirmed 169.254.169.254.nip.io and 127.0.0.1.nip.io both pass it (nip.io resolves <ip>.nip.io → that IP). So an attacker can make your server issue requests to internal/metadata addresses. Blast radius is softened (no auth headers sent, HTML-only content-type gate), but the SSRF primitive itself is live.

Fix: resolve DNS first and reject private/loopback/link-local ranges before connecting; pin the connection to the validated IP; re-validate on each redirect hop; cap response size.
P1Rate limiting is trivially bypassable — and vanishes entirely if Redis hiccups✓ verified in code

The per-IP limit keys on x-forwarded-for.split(',')[0] — the attacker-controlled first entry (Vercel appends the real IP to the end, so the code reads the spoofed value). A fresh fake header per request lands in a new bucket every time; the "3 per 24h" cap never engages. Separately, the rate-limit check fails open: any Redis error removes all limits. At 50 audits/hour global × 24h = 1,200 audits/day, at ~$1.35–4 each, that's up to ~$1,600–4,800/day of DataForSEO + OpenRouter spend a single actor could drive.

Fix: use Vercel's non-spoofable x-vercel-forwarded-for/x-real-ip; for the cost-relevant global cap, fail closed (or back it with a static Edge-Config ceiling).
P2The public results endpoint hands the lead's email to anyone with the URL✓ verified

GET /api/audit/<id> strips the raw LLM responses but then returns the entire record — including input.email (the lead's work email) and internal cost/diagnostic data. The audit ID is a random nanoid(12), so it's not guessable, but any time that URL is shared, logged, or forwarded, the submitter's email and your per-audit cost figures travel with it. The results page itself reads Redis server-side, so this endpoint doesn't need to expose email at all.

Fix: return an explicit public shape (scores, slides) and keep email, costs, traces, and errors out of the response.

4 · Design & mobile

You said it "doesn't look all too good." The deck is strong; the landing hero and mobile are where it slips — and it breaks the v3 design system in a few concrete ways.

P1The hero opens type-on-white — the exact hero your own v3 spec forbids

DESIGN.md §2 is explicit: pages OPEN on an electric-indigo stage (white-on-color), and lists as a "Never" a "quiet editorial type-on-white hero (where agency pages die)." The /ai-audit hero is dark text on a near-white ground with a plain bordered form card. It reads like a generic template landing page, not the immersive, high-craft LoudFace homepage. For the flagship lead magnet, that undersells the brand at the first impression.

Fix: restyle the hero as an electric-indigo stage per the homepage pattern — white headline, the form as a floating card on color. Route it through the /design loop rather than freehanding.
P2The site-wide Webflow badge sits on top of the form on mobile✓ confirmed live

A global fixed bottom-6 right-6 z-50 "Webflow Premium Partner" badge floats over page content. On the /ai-audit mobile view it lands directly on the "Your top 3 competitors" required field (see appendix). On the page whose entire job is form completion, a decorative third-party badge is obscuring the form.

Fix: hide the badge on /ai-audit (and any form-first page), or move it out of the form's column on small screens.
P2Two design-system violations in the deck: banned mono font (6×) and failing text contrast✓ verified

Mono font: font-mono is used 6 times (the "00 / 14" slide counter on every slide, the progress tagline, and four slides) — but Geist Mono is banned site-wide (two-font system only). Contrast: the muted caption tier text-surface-500 on the default slide background computes to 2.89:1 — below the 3:1 floor even for large text; the slide counter is worse (1.76:1). This hits nearly every label across all 15 slides.

Fix: drop font-mono everywhere (restyle counters as Satoshi + letter-spacing); lift muted text to surface-400 or brighter. The surface-500-on-dark pairing may be a token issue worth checking sitewide.
P2Mobile form inputs are 14px — iOS zooms in on every field focus✓ measured

Measured input font-size is 14px. iOS Safari auto-zooms any input under 16px on focus, then doesn't zoom back out — a jarring, well-known mobile-form friction on a 5-field form. Inputs also lack autoComplete/inputMode (the legacy form has them), so mobile autofill and keyboards are worse on the promoted form than the old one.

Fix: set input font-size ≥16px on mobile; add autoComplete="url"/"email"/"name" and inputMode="url".
P2The landing page renders the form twice with the same input IDs — clicking one label focuses the wrong field✓ verified

The /ai-audit page shows the form once in the hero and again near the footer. Both use hardcoded IDs (id="audit-url", audit-email, …), so the page has duplicate IDs. HTML label-to-input association resolves to the first match, so tapping the footer form's "Work email" label focuses the hero form's email field, scrolling the user away from where they were typing — a genuine, confusing focus bug on the conversion form.

Fix: generate per-instance IDs with React's useId(), or pass each form a unique id prefix.
P3The landing and the report live in two different visual worlds

The landing is crisp-light; the deck is fully dark. Not wrong, but the handoff is abrupt and neither references the v3 electric-indigo language that ties the rest of the site together. Worth a deliberate through-line once the hero is restyled.

5 · Reliability & correctness

Beyond the outage, the pipeline has a timeout ceiling it can blow and a few scoring bugs that can mislead a prospect.

P1Worst-case pipeline runtime is several times the 300-second function limit✓ arithmetic verified

The background job runs ~68 LLM calls across 3 sequential phases at concurrency 2. Two of every four platform calls (ChatGPT + Gemini via OpenRouter) have no timeout at all. Even counting only the calls that do have a timeout, worst-case is ~1,300s — over 4× the 300s Vercel cap. The happy path is 180–260s, which is why it usually works, but any upstream slowness pushes it past the cap, the function is killed, and the audit sticks at "processing" (feeding the P1 above).

Fix: add an AbortController timeout to the OpenRouter calls; add an overall pipeline deadline (~230s) that persists a partial result instead of dying; consider moving to a real background queue if you want headroom.
P2Brand-mention detection false-positives on common-word brand names✓ verified in code

mentionsBrand() is a word-boundary regex with no semantic check. For a brand like "Linear," "Ramp," "Wave," or "Notion," any ordinary use of the word ("a linear workflow") counts as a brand mention — inflating the visibility, discovery, and share-of-voice scores. The later LLM disambiguation pass only corrects the text sections, never the numbers underneath. So a customer with a common-word name gets a systematically overstated (or noisy) score — bad for a tool whose credibility is the number.

Fix: require a proximity signal (nearby "app/platform/company," preserved capitalization, or the domain) before counting a bare-word match.
P2A whole-phase outage silently reports the best-possible competitive rank (#1)✓ verified in code

If all of Phase 3 fails, the share-of-voice map is empty, and "Competitive Standing" falls through to its initial value of 1 — so the deck can show "Competitive Standing #1 of 4" (best possible) right next to Grade F and 0% discovery. An internally contradictory, falsely flattering number caused purely by missing data.

Fix: when the SoV map is empty but competitors exist, mark competitive standing "unavailable" instead of defaulting to #1.
P2Progress bar can visibly jump backwards

Progress is a whole-record read-modify-write called by 2 concurrent workers per phase; the later write wins even if it computed a lower number. Combined with unsequenced polling on the client (no abort, out-of-order responses committed), users can watch the bar go 60% → 40%. Cosmetic, but it reads as "broken" on a screen the user is already anxiously watching.

Fix: update progress via an atomic/monotonic write; drop out-of-order poll responses with a sequence guard.
P2The 15-slide report deck is not keyboard-navigable✓ confirmed live

Loaded the demo deck and tabbed through it: focus jumps from slide 3 to slide 8 to the sales CTA on slide 14 while the viewport never leaves slide 0 — 13 of 15 slides (the entire scorecard, gaps, competitor data, action plan) are unreachable by keyboard or screen reader, which land straight on the "Book a call" button. There's also no aria-live on the 3–5 minute progress screen, so assistive tech gets no updates the entire wait.

Fix: add arrow/Page/Space key handling + roving tabindex to the deck; make the progress dots real buttons; add role="status" aria-live="polite" to the progress text.
P2A results chart can add up to 133% — and two "overall" numbers don't mean what their labels say✓ verified in code

The cross-family review caught three numbers a sharp prospect would notice: the competitive-gap chart plots the brand's normalized share-of-voice next to competitors' raw mention rates under one label, so three "50%" bars can total 133%. Separately, a slide headlined "weighted average across all phases" actually displays only the Phase-1 discovery number, and the overall grade is described in the UI as including platform coverage but doesn't. On a tool whose credibility is its numbers, internally inconsistent figures undercut the pitch.

Fix: normalize all entities by the same denominator before charting; make each "overall/weighted" label reflect the value actually shown (or compute the value the label claims).

7 · What's genuinely good

Keep these — they're the foundation to build on

  • The report deck is the strongest asset. The per-query matrix (green check / red ✕ per platform), the severity stat cards ("35% Category Discovery Rate — Critical"), and the honest empty-states are clear, credible, and genuinely useful. This is what a prospect should see — the packaging around it is the problem, not this.
  • The three-phase methodology is real and defensible — branded queries, competitor "alternative-to" queries, unbranded category queries across 4 AI platforms, with a documented partial-data safeguard grounded in a real incident.
  • Backend scoring guards its math — every division is protected against zero/empty, so the 0-competitors case degrades gracefully rather than rendering "NaN."
  • Cost discipline exists — Haiku over Sonnet, trimmed query counts, concurrency throttling, per-call cost tracing (~55% cost cut already shipped).
  • Token/heading hygiene is clean — no raw hex, no default Tailwind colors, correct one-h1-per-slide hierarchy, no console/hydration errors.
  • The "no pressure, report first, call optional" framing is honest and on-brand — the sales CTA really is last, after the full report.
