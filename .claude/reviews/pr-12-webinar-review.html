Verdict: Request changes.

Solid page — clean server/client split, good metadata, components used correctly. But two issues will break in production: filled-in registrations get rejected by Notion (wrong property name, confirmed against the live DB), and the form's error message is invisible (uses a purged color token). Both are small fixes. The deeper note: an almost-identical feature already exists (/api/partner-apply + the ai-audit form) — mirroring it would have avoided most of these.

🔴 Blocking — will fail in production

Blocking
LinkedIn field breaks the submission — that property doesn't exist in the Notion DB
src/app/api/webinar-register/route.ts · the LinkedIn spread

The route writes LinkedIn: { url: linkedin } whenever the optional LinkedIn field is filled. Notion rejects any property key not in the database schema with a 400 → the route returns 500 → the user sees “Failed to save registration.” Only submissions that leave LinkedIn blank succeed (the property is conditionally spread).

Verified against the live DB (“Webinar Registrations”, 99b40712…): its properties are Name (title), Email, Company (text), Job Title (text), Consent (checkbox), Webinar (select), Registered At (created_time), and Company Website (url). There is no LinkedIn property. The Webinar option name and all other mappings match exactly — only this one is wrong.

// pick one:
- ...(linkedin ? { LinkedIn: { url: linkedin } } : {}),
+ ...(linkedin ? { 'Company Website': { url: linkedin } } : {}),  // reuse existing column
//   …or add a LinkedIn (url) property to the DB and keep the key.
//   Decide which: the form asks for LinkedIn, the column says Company Website.

Note: Notion also rejects a malformed url value, so validate/normalise the LinkedIn input too (the field is type="url" but accepts linkedin.com/in/... without a scheme).

Blocking
The error message is invisible — red-* tokens are purged in this project
_components/WebinarRegistrationForm.tsx · bg-red-50 … text-red-600

The inline error uses className="rounded-lg bg-red-50 px-4 py-3 text-sm text-red-600". In globals.css the entire red palette is cleared with --color-red-*: initial, and the comment there literally says such classes “silently do nothing.” So the error box renders with no background and inherited text colour — users get a failed submit with no visible feedback.

Use the project semantic tokens — --color-error / --color-error-light exist for exactly this (globals.css).
- className="rounded-lg bg-red-50 px-4 py-3 text-sm text-red-600"
+ className="rounded-lg bg-error-light px-4 py-3 text-sm text-error-dark"

🟠 High — wrong behaviour / breaks house conventions

High
Wrong env var name — diverges from the Notion integration that's already deployed
src/app/api/webinar-register/route.ts · process.env.NOTION_TOKEN

The route invents NOTION_TOKEN. The existing, working Notion route (/api/partner-apply) reads NOTION_API_KEY — already set in Vercel. The PR's “Arnel must add NOTION_TOKEN before publishing” step is likely unnecessary: reuse NOTION_API_KEY and share the Webinar Registrations DB with that same integration. At minimum, match the established name so there aren't two Notion secrets.

High
PostHog event almost certainly never fires (and leaks raw email)
_components/WebinarRegistrationForm.tsx · (window as any).posthog

The project lazy-loads posthog-js via dynamic import and keeps it out of the initial bundle — window.posthog is not the access path and is likely undefined at submit, so webinar_registered silently no-ops. Every other form (ai-audit, partner-apply) uses the same pattern; mirror it. Also: the house convention sends email_domain in capture props and reserves the raw email for identify() — this PR puts raw email in the event properties.

- if (typeof window !== 'undefined' && (window as any).posthog) {
-   (window as any).posthog.capture('webinar_registered', { email: data.email, … });
- }
+ void import('posthog-js').then(({ default: posthog }) => {
+   if (!posthog.__loaded) return;
+   posthog.identify(data.email.toLowerCase());
+   posthog.capture('webinar_registered', {
+     email_domain: data.email.split('@')[1] ?? '', company: data.company,
+     job_title: data.jobTitle, webinar: 'ai-search-visibility-july-2026',
+   });
+ });

🔵 Medium

Medium
Event start time is an hour off — JSON-LD contradicts the calendar link
page.tsx · EVENT_JSON_LD.startDate vs the form's GCAL_URL

JSON-LD says 2026-07-09T11:00:00-05:00 (= 16:00 UTC). The Add-to-Calendar link says 20260709T150000Z (= 15:00 UTC = 11:00 AM Eastern). July 9 is on EDT (UTC-4), not EST, so the JSON-LD offset is wrong by an hour. The calendar link is right; fix the schema offset to -04:00. (The “EST” in the copy is also technically EDT in July — “ET” is the safe label.)

- startDate: '2026-07-09T11:00:00-05:00',  endDate: '2026-07-09T12:00:00-05:00',
+ startDate: '2026-07-09T11:00:00-04:00',  endDate: '2026-07-09T12:00:00-04:00',
Medium
Event schema will fail Google's rich-result validation — missing location
page.tsx · EVENT_JSON_LD

With eventAttendanceMode: OnlineEventAttendanceMode, Google requires a location of type VirtualLocation with a url; without it the Event is invalid in the Rich Results Test. For an agency whose whole pitch is AEO/SEO, their own event markup should validate. Worth adding performer (the two speakers) and an image too.

+ location: { '@type': 'VirtualLocation', url: 'https://loudface.co/webinar/ai-search-visibility' },
+ performer: [{ '@type': 'Person', name: 'Arnel Bukva' }, { '@type': 'Person', name: 'Natalie Sangkagalo' }],
Medium
Success state promises a confirmation email that nothing sends
_components/WebinarRegistrationForm.tsx · success copy + consent label

“Check your inbox for confirmation” and the consent line (“Send me the recording…”) imply an email flow, but the route only writes a Notion row — no email is sent (same as partner-apply). Either wire a confirmation (Resend / a Notion automation) or soften the copy to “We'll email you the join link before July 9.” Don't promise an inbox event that doesn't exist.

Medium
Failure mode is inverted vs the house pattern — a Notion blip = lost lead
route.ts vs partner-apply/route.ts

partner-apply deliberately returns success even if Notion is down (“a Notion outage should not look like a form failure”) and writes best-effort. This route hard-500s to the user with no fallback capture, so any Notion hiccup loses the registration and shows a scary error. Decide intentionally: if you want guaranteed capture for a webinar seat, add a fallback (email/secondary store) rather than only surfacing the failure.
