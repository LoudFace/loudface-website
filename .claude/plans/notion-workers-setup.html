Deploy Notion Workers for the LoudFace content index

Code is written, typechecked, built. What's left is the parts only you can do: enable the Workers feature in your workspace, get three API credentials, push them to Notion, and deploy. Every step has the exact command to run.

What you'll end up with

  • A new Notion database called Live Site Index, auto-created by the worker on first sync.
  • Three syncs running on Notion's hosted runtime:
    • sanitySync hourly — Title, URL, Content Type, dates, Meta Description.
    • gscMetrics every 6h — clicks, impressions, position (7d).
    • peecCitations every 6h — AI citation count + rate (7d).
  • The existing Website Content calendar untouched — it stays the editorial pipeline (Idea / Outline / Draft / Review / Published).

Steps

1
You · 30 seconds

Enable the Workers feature in your workspace

Workers is in beta and gated per workspace. Run an interactive workers command — the CLI will prompt you to enable it, redirect you to a Notion page, you click "Enable", done.

cd "/Users/arnel/Code Projects/LoudFace Agency/loudface-website/scripts/notion-workers"
ntn workers list

If it prompts "Workers not enabled — open in browser to enable?", say yes. Otherwise it's already on.

2
You · 5 minutes

Get a Google Cloud service account for GSC read access

The worker needs a service account key (not OAuth — server-to-server). Quickest path:

  1. Go to console.cloud.google.com/iam-admin/serviceaccounts.
  2. Pick or create a project (any name, e.g. loudface-workers).
  3. Create a service account: name gsc-reader, no roles needed.
  4. On the new account: Keys → Add key → Create new key → JSON. Download.
  5. Enable the GSC API for the project: enable here.
  6. Go to search.google.com/search-console/users, pick https://www.loudface.co/, click Add user, paste the service account email (looks like gsc-reader@loudface-workers.iam.gserviceaccount.com), permission: Restricted.

The whole JSON file goes into one env var. Keep it locally for now, we push it in step 4.

3
You · 2 minutes

Get a Peec AI API token

  1. Go to app.peec.ai, log in to the LoudFace project.
  2. Settings → API Keys → Generate new key.
  3. Copy the token. It won't be shown again.
4
You · 2 minutes

Set the three secrets

The Sanity token is already in .env.local of the main project. Reuse it.

# From the workers project dir:
cd "/Users/arnel/Code Projects/LoudFace Agency/loudface-website/scripts/notion-workers"

# 1. Sanity — pull the existing token
SANITY_TOKEN=$(grep '^SANITY_API_TOKEN=' ../../.env.local | cut -d= -f2-)
ntn workers env set SANITY_API_TOKEN="$SANITY_TOKEN"

# 2. GSC — paste the FULL JSON contents of the key file you downloaded
# (single-quote it so $ chars in the JSON don't get expanded)
ntn workers env set GSC_SERVICE_ACCOUNT_JSON='{"type":"service_account",...}'

# 3. Peec
ntn workers env set PEEC_API_TOKEN='your-peec-token-here'

# Verify all three are stored
ntn workers env list
Secrets are encrypted at rest in Notion's vault and exposed to the worker runtime as process.env.*. They never appear in the deployed code.
5
Auto · 1 minute

Deploy the worker

ntn workers deploy

This compiles + uploads. You should see something like:

[build] Deploying...
[build] Uploading to Notion...
[build] Worker updated...

Capabilities:
  sync  sanitySync
  sync  gscMetrics
  sync  peecCitations
6
Auto · 2 minutes

Trigger the initial sanity sync to populate the new database

First time around, kick the sanity sync manually so the Live Site Index database appears in Notion. After that the hourly schedule takes over.

ntn workers sync trigger sanitySync

Watch it complete:

ntn workers sync status

You should see HEALTHY within ~30 seconds and a new Live Site Index database in Notion with ~104 rows.

7
Auto · 1 minute

Trigger the metric syncs once so the first numbers land

ntn workers sync trigger gscMetrics
ntn workers sync trigger peecCitations
ntn workers sync status

Two more HEALTHY rows. The Live Site Index is now fully populated and on auto-pilot.

8
Optional · later

Clean up the old Website Content calendar

Now that the Live Site Index is the source of truth for live content + metrics, the 100+ rows we backfilled into the original calendar are duplicates of what the worker manages. Two options:

  • Keep them — calendar shows everything in one place. Manual cleanup needed periodically.
  • Delete the Published rows — calendar shrinks back to ~19 active editorial entries (Idea/Outline/Draft/Review). The Live Site Index covers published.

Recommend option two — that's the clean separation the migration was designed for. I can run a one-shot delete script when you're ready.

Sanity checks after deploy

# See what's deployed
ntn workers list
ntn workers capabilities list

# Inspect last run logs for any sync
ntn workers runs list --plain | head -n3
ntn workers runs logs <runId>

# Preview a sync without writing (debugging only)
ntn workers sync trigger sanitySync --preview

# If something's stuck, reset cursor + retry
ntn workers sync state reset gscMetrics
ntn workers sync trigger gscMetrics

Common failure modes

If you see… Fix
GSC token exchange failed: 400 The service account isn't added to GSC users for www.loudface.co. Re-do step 2 line 6.
GSC query failed: 403 The GSC API isn't enabled for the project. Enable it.
Peec fetch failed: 401 Wrong/expired Peec token. Regenerate at app.peec.ai → Settings → API Keys.
Sanity fetch failed: 401 Token expired or didn't get copied correctly. Re-run step 4 line 3.
Live Site Index not appearing The first sanitySync run creates it. Trigger it manually: ntn workers sync trigger sanitySync.
