Migrate the LoudFace content calendar to Notion Workers

Replace the Claude-Cloud-scheduled /refresh-calendar skill with three native Notion Workers running on Notion's infra. Why: airtight schema, persistent cursors, atomic upserts, hosted runtime, fewer moving parts. Trade-off: Workers is in beta, and there's 2-3 hours of one-time setup.

Why migrate

The current setup works, but four pain points keep showing up:

  1. Token-burning runs. Each /refresh-calendar execution makes 100+ MCP roundtrips. Cloud subscription pays the bill.
  2. View pagination cap. Notion's query-database-view returns max 100 rows. With 104+ Published rows, a single run misses some.
  3. No persistent cursor. Every run pulls everything, re-computes everything, writes everything. No idea of "what changed since last run."
  4. Field gaps from initial backfill. 75 rows were missing Meta Description and Last Updated until just now. A declarative schema would have caught that on day one.

Notion's new Developer Platform (announced 2026) gives us three primitives that solve all four:

Syncs
↻
Continuously upsert external records into a DB with a declarative schema and persistent cursor.
Agent tools
⚒
Custom tools for Notion Agents that query live data or hit any API.
Webhooks
⇆
Listen for events from external systems, trigger Notion workflows.

All three run on Notion's hosted Workers runtime — isolated sandboxes managed by Notion. No Vercel cron, no Lambda, no Claude Cloud burn.

Before

  ↓

After

// Three independent workers running on Notion's runtime

Worker 1: sanitySync       schedule: "1h"    // auto-syncs new posts
Worker 2: gscMetrics       schedule: "6h"    // GSC clicks/imp/pos
Worker 3: peecCitations    schedule: "6h"    // Peec AI mentions

  ↓ each one is atomic and idempotent
  ↓ each one declares its own schema (no drift)
  ↓ each one uses a persistent cursor (only re-syncs deltas)
  ↓
Notion DB: Website Content (schema-as-code, airtight)

The three workers

Worker 1 — sanitySync.ts

Source of truth for: Title, URL, Content Type, Publish Date, Meta Description, Last Updated. Runs hourly. Never touches Status (preserves editorial pipeline).

import { Worker, Schema, Builder } from "@notionhq/workers";
import { createClient } from "@sanity/client";

const worker = new Worker();

const calendar = worker.database("website-content", {
  type: "managed",
  primaryKeyProperty: "URL",
  schema: { properties: {
    "Title": Schema.title(),
    "URL": Schema.url(),
    "Content Type": Schema.select([
      { name: "Blog Post" }, { name: "Listicle" },
      { name: "Case Study" }, { name: "Landing Page" },
    ]),
    "Publish Date": Schema.date(),
    "Last Updated": Schema.date(),
    "Meta Description": Schema.richText(),
    "Status": Schema.status({
      groups: { complete: ["Published"], in_progress: ["Draft", "Review"] }
    }),
  }}
});

const sanity = createClient({ projectId: "xjjjqhgt", dataset: "production" });

worker.sync("sanitySync", {
  database: calendar,
  schedule: "1h",
  execute: async () => {
    const docs = await sanity.fetch(`
      *[_type in ["blogPost", "caseStudy"] && defined(slug.current)] {
        _id, _type, slug, name, publishedDate, lastUpdated, metaDescription
      }`);

    return {
      changes: docs.map(d => ({
        type: "upsert",
        key: buildUrl(d),  // primary key — no dupes, ever
        properties: {
          "Title": Builder.title(d.name),
          "URL": Builder.url(buildUrl(d)),
          "Content Type": Builder.select(classify(d)),
          "Publish Date": Builder.date(d.publishedDate),
          "Last Updated": Builder.date(d.lastUpdated),
          "Meta Description": Builder.richText(d.metaDescription),
          // Status only set on FIRST upsert, never overwritten
          "Status": Builder.statusInitial("Published"),
        }
      }))
    };
  }
});

Worker 2 — gscMetrics.ts

Pulls last-7-day GSC analytics, paginated. Upserts metrics into existing rows by URL. Never creates new rows.

worker.sync("gscMetrics", {
  database: calendar,
  schedule: "6h",
  execute: async ({ env }) => {
    const pages = await gscSearchAnalytics({
      siteUrl: "https://www.loudface.co/",
      startDate: daysAgo(7),
      endDate: today(),
      dimensions: ["page"],
      rowLimit: 1000,
      auth: env.GSC_SERVICE_ACCOUNT_KEY,
    });

    return {
      changes: pages.map(p => ({
        type: "update",  // update-only, won't create
        key: p.page,
        properties: {
          "GSC Clicks 7d": Builder.number(p.clicks),
          "GSC Impressions 7d": Builder.number(p.impressions),
          "GSC Position 7d": Builder.number(p.position.toFixed(1)),
          "Last Refreshed": Builder.date(today()),
        }
      }))
    };
  }
});

Worker 3 — peecCitations.ts

Same shape, different source. Pulls Peec URL report for loudface.co domain, updates the Peec Mentions column.

worker.sync("peecCitations", {
  database: calendar,
  schedule: "6h",
  execute: async ({ env }) => {
    const data = await peecUrlReport({
      projectId: "or_85a7fe4b-9032-4b0f-8b98-6deae65495ff",
      domain: "loudface.co",
      startDate: daysAgo(7),
      endDate: today(),
      token: env.PEEC_API_TOKEN,
    });

    return { changes: data.rows.map(r => ({
      type: "update",
      key: normalizeUrl(r.url),
      properties: { "Peec Mentions": Builder.number(r.citation_count) }
    }))};
  }
});

Setup checklist

One-time work to get this running. Total: ~2-3 hours.

  • Install Notion CLI · npm install -g @notionhq/cli · 5 min
  • Authenticate the CLI to your workspace · ntn auth login · 2 min
  • Create new project dir · scripts/notion-workers/ with the Workers SDK · 10 min
  • Add API tokens to Worker env (encrypted in Notion's vault):
    • SANITY_API_TOKEN — already in .env.local, just copy it across
    • GSC_SERVICE_ACCOUNT_KEY — needs new Google Cloud service account with read-only GSC access. Most involved step (~30 min)
    • PEEC_API_TOKEN — from app.peec.ai API settings (5 min)
  • Write Worker 1 (sanitySync) · ~45 min · simplest, validates the setup
  • Deploy + smoke test · ntn deploy worker · 10 min
  • Write Worker 2 (gscMetrics) · ~45 min
  • Write Worker 3 (peecCitations) · ~30 min
  • Disable old /refresh-calendar Cloud schedule · 2 min
  • Update CLAUDE.md + brain page with new architecture · 10 min

Decision

Option A — Migrate to Notion Workers Recommended for long-term
2-3 hours setup · solves all 4 pain points · accepts beta risk
Build the three workers. Disable Cloud schedule. The calendar becomes truly hands-off.
Option B — Harden current skill on Vercel cron Middle ground
~90 min setup · solves pagination + idempotency · adds Notion REST API integration token
Create a Notion internal integration. Build one Node script that does Sanity sync + GSC + Peec writes via REST API. Run via Vercel cron. No Notion beta dependency. Less elegant than Workers, more proven.
Option C — Keep current and just schedule it Lowest effort
10 min setup · works for now · doesn't fix pagination root cause
Add the /schedule cron, document the 100-row cap as a known limitation. Revisit when Workers ships GA or the calendar grows past ~200 rows.

My recommendation is Option A, but it depends on appetite for one beta-feature dependency. If the answer is "I want airtight and I'm comfortable with beta," go A. If the answer is "I want airtight but I want it on infra I already trust (Vercel)," go B.
